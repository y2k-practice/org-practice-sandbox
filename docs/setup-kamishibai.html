はじめに

GitHub 練習環境をつくろう

会社の AI 駆動開発を、自宅で先に練習する紙芝居です。

所要時間の目安: 1〜2 時間。途中で止めても、続きから再開できます。
なぜやるの？

「自分の PC」から「リポジトリが正本」へ

  • 設定がリポジトリにあれば、新メンバーも同じ状態で始められます。
  • 最終承認は人。AI は作業者であって、承認者にはなりません。
全体マップ

6つの場面で進みます

アカウント作成・規約への同意・パスワードやトークンの入力は、Claude は代行しません。

登場人物

2つのアカウントで、3つの役を練習します

GitHub では PR の作成者は自分の PR を承認できません。2アカウントでも「書く人」と「承認する人」は分かれるので、練習として成立します。足りないのは、dev と admin を分ける練習だけです。
場面1

gh（GitHub CLI）を入れる あなた

  1. スタートメニューから PowerShell を開く。
  2. 次のコマンドを貼り付けて Enter。
  3. 「インストールが完了しました」と出たら終わり。
winget install --id GitHub.cli --exact

確認済み: winget で GitHub CLI 2.103.2 が入手できます。

ダウンロードを伴うため、Claude は実行せず、あなたが実行します。
場面1

ターミナルを開き直して、ログイン あなた

  • 表示される文言が少し違っても、GitHub.com → HTTPS → ブラウザの選択肢を選べば大丈夫です。
  • ブラウザで GitHub にログイン済みなら、コードを入れて承認するだけです。
認証コードの入力と承認は、あなた自身の操作です。トークンやパスワードをチャットに貼らないでください。
場面1の確認

入ったかどうかを確かめる

gh --version
gh auth status

2つ目で、Logged in to github.com account … と出ればOKです。

出た表示対処
gh が見つからないターミナルを閉じて開き直す
not logged ingh auth login をやり直す
場面2

Organization を作る あなた

次の URL を開きます（画面は実際に確認済み）。

https://github.com/account/organizations/new?plan=free
項目入力
Organization name例: y2k-practice
Contact email連絡用メール
belongs toMy personal account
Terms of Service読んで同意にチェック
入力と同意は、あなた自身の操作です。Next の後に出る招待画面は、いったんスキップで構いません。
場面2のコツ

名前と料金プランの考え方

  • 名前: 英数字とハイフン。後から変えられますが、URL が変わるので最初に決めておく。
  • プラン: Free で十分。SSO や監査ログなど Enterprise 限定機能は、本番で差分を確認します。
  • 連絡先メール: 個人用で問題なし。
  • 作り終えたら、Org のページが github.com/<org名> で開くことを確認。
Enterprise の機能は自宅では再現できません。ここでは「型」を覚えることが目的です。
場面3

reviewer を招待する あなた

Org のページ → People から Invite member でユーザー名かメールを入れて招待します（画面の文言は変わることがあります）。

GitHub は、一人が複数の無料アカウントを持つことを規約上は原則禁止しています。reviewer は家族や知人など、別の人に頼むのが安全です。自分で2つ目を作る場合は、公式の規約を確認してから判断してください（Claude は作成を代行しません）。
場面4

リポジトリを Org に置く Claude

push 前の安全確認（Claude が実施）

  • 秘密情報が履歴に無いか（gitleaks 相当の確認）
  • .env などが追跡対象外か
  • 公開してよい内容か
最初は public が無難です。無料 Org の private ではブランチ保護の一部が使えない場合があります。公開は外部への発信なので、実行前にあなたの「はい」を待ちます。
しくみ①

ファイルの「置き場」は3つあります

しくみ②

ブランチ＝「main を汚さない作業台」

  • 失敗しても、main は無傷です。ダメなら枝ごと捨てられます。
  • 枝を main に戻すための「お願い」と「確認」の場が、Pull Request です。
しくみ③

Pull Request の一生

実例

いま起きていること（PR #1）

用語ひとこと
commitPC の中で変更を記録する
push / pullPC → GitHub に送る ／ GitHub → PC に取り込む
branchmain を汚さない作業台
Pull Request「この枝を main に取り込んで」という GitHub 上の依頼
merge承認後に、実際に main へ取り込むこと
場面5

CODEOWNERS を実アカウントに Claude

承認者の名簿です。2アカウントでは、自分の PR を自分で承認できないため、全パスの承認者を reviewer にします。

書いてある名前置換先
@REVIEWER_ACCOUNTreviewer のアカウント
@ADMIN_ACCOUNTreviewer のアカウント（同じ）

この変更自体を、ブランチ → PR → レビュー → マージで行い、最初の練習題材にします。

場面6

main に4つの鍵をかける あなた一緒に

  1. リポジトリ → Settings → Rules → Rulesets を開く。
  2. New ruleset から Import a ruleset を選ぶ。
  3. docs/branch-ruleset.json を選んで、内容を確認して作成。

画面の文言は変わることがあります。実画面を見ながら一緒に進めます。

その後

ちゃんと止まるか、わざと試す

6つの演習は docs/failure-drills.md、計測の表は docs/metrics.md にあります。「止まった／止まらなかった」と原因を書き残すことが、会社への最大の持ち帰りになります。
